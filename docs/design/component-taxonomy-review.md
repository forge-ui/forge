# Forge 组件迁移分类复核

> 2026-10-14 更新：本文保留为历史分类讨论。最新 123 项融合决策以 [组件融合审查](./component-fusion-audit.md) 和 [审查 JSON](./component-fusion-audit.json) 为准；下文旧的独立组件建议已被覆盖，不代表当前实现、用户验收或发布。

状态：分类提案，尚未应用到导航或迁移计划。2026-10-13。

本轮核对实验室保留的 117 个原型及 6 个 Forge 延展示例，共 123 项；以原型的主体结构、交互脚本和 core 的实际 API 为依据。这是源码和分类复核，不代表 123 项都完成了浏览器交互验收，也不代表迁移完成。

## 问题出在哪里

此前的分类表把三个问题混成了一个 `family`：用户到哪里找、组件复用谁、完整示例完成什么任务。结果是用容器外形、底层依赖或组件名字代替了实际交互判断。

实验室 `scripts/organize.py` 的 `blocks` 按编号区间指定家族和目标组件，再用导出名称的正则匹配判断是否已有组件。这个脚本可以生成清单，却不能证明语义相同。例如 079–085 一起映射到 ProgressBar，包含骨架加载与下拉刷新；044 Accordion 被放进 modal；186 设备发现被映射到 OtpInput。随后生成的源码签名和通用验收项不能补足这些判断。

应停止沿用这张表作为自动迁移依据。新提案与现行表并存，确认后才更新实验室分类，避免生成脚本再次覆盖人工结论。

## 分类规则

1. **主入口按用户寻找的功能确定。** 先描述操作对象、触发动作和结果，再确定分类。动画方式、文件路径、容器形状都不是主分类依据。
2. **一个功能只有一个主展示入口。** 其他使用场景提供关联链接，不重复维护独立组件。例如批量操作主要放列表，表格和智能体列表链接复用。
3. **组件与完整示例分别归属。** 统计卡里的数字滚动是卡片能力；完整实时看板可能组合图表。不能因为拆出一个数字组件，就宣称原看板迁移完毕。
4. **复用要核对状态和回调。** 外观近似、名字近似或导出存在，都不等于支持所需交互。记录现有能力和缺少的契约，再决定扩展、组合、新增或暂缓。
5. **优先已有组件的变体和案例。** 新组件必须有独立、稳定、可复用的输入输出；业务流程先留在 cases。
6. **没有合理归属就明确暂缓。** 不再用“智能体”“卡片”“实用组件”兜底；已经要求删除的系统类内容不能换个类名重新纳入。

每项记录：实际任务、官网主入口、组件能力、完整示例归属、复用对象、迁移方式、交叉索引、依据及未解决问题。官网只展示简洁的主入口和相关示例，不把这些内部审查字段全部塞给访问者。

## 分类粒度修订：这轮不增加侧栏入口

上一版列出了能力边界，但这些边界不应各占一个侧栏入口。官网采用一个家族入口，页面里保留清晰的组件小节，变体放在对应组件下；不再为每个状态或业务示例增加导航层级。

| 位置 | 应承载的内容 | 示例 |
| --- | --- | --- |
| 侧栏入口 | 用户熟悉、边界稳定的一组能力 | 按钮与链接、表单与输入、卡片、列表、提示与反馈 |
| 页内小节 | 具体组件或明确能力，支持直达锚点 | Button、统计卡片、批量操作、Tooltip、ProgressBar、EmptyState |
| 小节内示例 / 案例标签 | 变体、动效或业务场景 | 长按删除、数值滚动、归档撤销、文件夹空态；协作流程、内容编辑 |

本轮具体收敛：

- **提示与反馈**替代原“进度”入口，并吸收“提示气泡”，而不是另加一个“反馈与状态”入口。页内明确列出提示气泡、行内提示与公告、通知消息、加载与进度、空态与结果。分类合并不意味着 Tooltip、Toast、ProgressBar、EmptyState 合并成一个 API。
- **弹窗与抽屉**保留独立入口。它涉及打开/关闭、模态焦点及复杂内容承载，边界足够明确；不继续往反馈页塞。由原“确认弹窗”扩展名称，不增加入口。
- **菜单与导航、布局与容器**只是调整原“菜单、布局栅格”的收纳边界；新增能力优先作为这些页面的小节。
- **内容与编辑、协作与流程**仅作为实验室/cases 的标签，明确不建设同名组件侧栏入口。暂缓、排除也只是审核状态，不是官网分类。
- **交互动效**转到文档说明和索引；**实用组件**在逐项建立准确入口后退出侧栏。仅完成迁移后撤下旧入口，旧 URL 和组件链接仍需能定位。

进度、Tooltip 等熟悉的词要保留在页内目录、检索关键词和直接链接中，不能为了减少入口而藏掉它们。图表、文件上传、列表刷新仍保留原主入口，只有共用的状态表现关联到提示与反馈。

分类数量不按原型数量决定：14 个按钮演示不构成 14 类；一个成熟复杂家族也不因本轮只增加一个示例就被强并。以后只有在现有入口无法解释用户查找意图、存在稳定的通用能力群、且页内小节与关联链接确实不足时，才考虑新增入口。

## 现有目录如何容纳新增内容

保留大部分现有分类及可直达的 URL。以下表格描述功能边界；原来的进度、提示气泡合并到提示与反馈，其他能力优先进入页内小节，不要求每个 demo 都变成新的 core 导出。

| 目录 | 收纳边界 | 不放什么 |
| --- | --- | --- |
| 按钮与链接 | 按压、长按、提交、复制等动作触发及按钮变体 | 含多步业务状态的完整发布或审批流程 |
| 表单与输入 | 输入值、选择值、校验、上传；验证码、标签输入、日期范围、成员选择 | 日期排程、审批流程、订阅计费业务 |
| 筛选 | 缩小结果集的条件、范围、搜索结果恢复 | 所有带搜索图标的控件 |
| 卡片 | 统计、实体摘要、任务/用户摘要的卡片呈现与局部交互 | 仅仅有圆角背景的空态、通知、对话框；FileCard 主入口在文件展示，卡片仅索引 |
| 列表 | 集合条目、选中、批量操作、滑动操作、刷新 | 二维行列单元格数据、通用提示反馈 |
| 数据表格 | 列、行、单元格、排序、表格选择、权限矩阵 | 没有表格结构的文件批量操作 |
| 图表 | 编码数据关系、比较、趋势与分布的可视化 | 普通数字滚动、完成百分比条 |
| 日历与日程 | 日期浏览、事件排布、时段可用性、日程编辑 | 作为表单值输入的日期范围选择（主入口在表单，日历给关联链接） |
| 文件展示 | 文件类型、文件卡片、文件内容预览 | 上传过程（主入口在表单）、完整消息输入框 |
| 菜单与导航（由“菜单”调整） | 下拉/上下文菜单、侧栏、底部导航、命令面板 | 因数据叫任务或智能体就归入 agent |
| 布局与容器（由“布局栅格”调整） | 网格、分栏、可折叠内容和结构容器 | FAQ 问答内容本身、弹窗确认流程 |
| 弹窗与抽屉（由“确认弹窗”调整） | Modal、Drawer、ConfirmationDialog | Toast、行内提示、Accordion |
| 提示与反馈（整合原进度、提示气泡） | Tooltip、行内提示、Toast、骨架、加载与进度、空态和结果；各有独立小节和组件契约 | 历史事件、数据图表、数字滚动、列表刷新、语音活动；业务恢复流程放 cases |
| 聊天 | 消息、引用回复、表情反应、输入框、语音输入 | 通用成员管理、普通业务列表 |
| 智能体 | 推理与执行过程、工具调用、生成内容、人机决策的专用组合 | 通用搜索、通用审批、团队分派、设备配对 |
| 历史记录 | 版本、操作记录、时间线、回溯 | 当前步骤的百分比、普通表单校验 |
| 评论与评价 | 评论、评分、用户评价与反馈内容 | 通用输入框和卡片容器本身 |

其余保留：徽章与标签、待办清单、地图、页面顶栏、分页与步骤、页签与切换、工具栏。叶类下通过小节区分能力，不增加无必要的导航层级。暂不因本轮涉及示例少就继续合并这些成熟类别，避免一次改动过多入口。

“交互动效”应改成用法说明和索引：按钮动效回到按钮，验证码回到表单，CalendarCard 回到日历，LiquidTabs 回到页签，AddMember 回到成员选择的主入口。动效仍保留，文档位置不应强迫用户先猜它是否属于动画组件。

“实用组件”停止接收新项目。已有 RatingStars 对应评论与评价、ProductRow 对应列表；CurrencyConverter 是表单组合案例；ImageGrid 对应文件/图片内容展示。逐项建立新入口与关联链接后再考虑隐藏旧导航，不能先删入口造成找不到。

**内容与编辑、协作与流程只作为实验室/cases 的标签。** 这些原型确实有独立用途，但目前多数缺少生产 API 契约；这轮不新建同名组件目录。未来是否成为正式组件家族，需要重新验证查找需求和能力边界，不因迁移清单已经用了这两个词而自动升级。

整理分区不是迁移承诺。188 灰度发布、189 环境晋级等运维示例仍暂缓，不借“协作与流程”恢复已要求删减的系统类或冷门项目。061 图片预览仍需在文件预览场景下复核必要性，先不列为生产迁移项。

## 接下来按什么顺序迁移

1. 确认这一版归类原则和逐项对照；先在实验室展示新主入口与交叉索引。仅修改主分类的项目不触碰其已确认的视觉和动效。
2. 先迁已有家族能承接的变体与案例：按钮、表单、菜单、卡片、列表、反馈状态。每次同时核对原型主交互、core 状态回调和官网可查找性。
3. 同类原型收敛为一个实现：例如 178/F03 批量操作，088/089/090/092/F06 的状态展示与恢复案例。收敛不等于把不同恢复动作写死进同一个组件。
4. 图表、编辑器、协作流程逐项评估；保留在实验室的项目明确标记暂缓，不能用“已对应组件”掩盖能力缺失。
5. 分类只调整文档入口，不自动改包导出、升级版本、发布或删组件。发布仍要单独完成代码、交互、类型与包体积检查。

上述步骤继续遵守既定约束：保留已确认原型的主要交互和动效；默认中文并支持英文；字体、字号、字重、文字颜色和蓝/紫/黑主题对齐 Forge；通用图标优先 Solar。分类正确不能替代这些验收。
