## 必须修复

### 1. P1：审批单选快速改选会跳过整个问题

- 类型：功能错误，浏览器确认。
- 路径：`/cases/agent#approvalcard`，第一题连续点击“三项推荐”和“五项推荐”。
- 结果：先进入 2 / 3，随后自动进入 3 / 3，用户没有机会填写多选的第二题。
- 来源：`core/src/components/ui/agent/approval-card.tsx:50–72`，每次单选都新增一个 280ms 定时器，两个定时器各累加一次 index，且不会因改选或切题而取消。
- 影响：正常犹豫改选会被误认为答完多题，可能提交不完整答案。
- 建议：只保留一次当前题的自动前进；改选、手动前后题、提交和卸载都取消待执行任务。最后一题自动提交还捕获旧 answers（同文件 62、69 行），须以回调测试单独确认并修复；现有 case 没接 onSubmitted，无法从 UI 核对回调载荷。

### 2. P2：附件已上传，仍不能只发送附件

- 类型：明确交互缺口，浏览器确认。
- 路径：`/cases/chat#interaction-F01`，保持文字为空，连续两次“推进进度”把初始附件从 35% 推至 100%。
- 结果：显示“已上传”，发送按钮依然 disabled，必须输入任意文字才能发送。
- 来源：`src/app/components/_fusion/agent-charts.tsx:87` 已解除上传中的 sendDisabled，但 `core/src/components/ui/chat-input-bar.tsx:339` 和 `:391` 仍要求非空 trimmed 文本；attachments 仅是展示插槽。
- 影响：常见的直接发文件操作被无提示阻止，用户可能误以为上传尚未完成。
- 建议：用明确的“存在可发送非文本内容”状态驱动发送有效性；保留空消息、未完成上传的阻止逻辑，避免通过 ReactNode 是否存在推断有效附件。

### 3. P2：默认中文案例仍大量出现英文操作和任务状态

- 类型：明确文案一致性缺陷，浏览器确认。
- 路径：`/cases/agent` 默认中文；任务仍显示 Completed / Running / Failed，审批有 Skip / Continue 和英文问题，建议有 High confidence / Other options / Accept，检索有 All chunks / characters，洞察有 Previous insight / Next insight。
- 来源：`core/src/components/ui/agent/agent-task-rows.tsx:34–38`；`approval-card.tsx:23–29`；`recommendation-card.tsx:25–40`；`context-cards.tsx:22`；示例数据见 `src/app/cases/agent/page.tsx:39`、`:110–143` 等。
- 影响：核心动作与状态中英文混杂，普通用户对“可点什么、是否已完成”的理解不统一。
- 建议：组件默认中文、显式 locale 或统一 labels 支持英文；同步案例数据和说明，保留必要的 API 名称与代码内容。

### 4. P2：原生智能体案例部分主要操作没有任何反馈

- 类型：案例接线缺陷，浏览器确认、源码确认。不是要求演示调用真实后端。
- 路径：`/cases/agent#recommendationcard` 点击 Accept；`#insightcards` 点击“调整周末冷柜库存”。
- 结果：按钮可点，但页面没有确认、选中、草稿或下一步变化。RecommendationCard 的备选也未接回调。
- 来源：`src/app/cases/agent/page.tsx:245–252` 缺 onAccept/onSelectAlternative；`:303–320` 缺洞察建议回调。相对地，AgentDiffTable 点击 Apply 确实变为“2 edits applied”，不能把它列为无反馈。
- 影响：用户无法判断点击是否成功，容易反复点击，也看不出组件真正能力。
- 建议：接入本地状态即可；接受后显示已接受和重置，备选更新当前方案，洞察建议生成一条可见的后续问题或草稿。

## 需改清楚的展示语义

### 5. P2：工作分派把全局分派比例放在下一项任务的“进度”下

- 类型：明确信息歧义，浏览器确认。
- 路径：`/cases/card#interaction-181`，初始“首页无障碍检查”0%，给林晓分派一次。
- 结果：标题立即变为“整理品牌规范”，其下显示“进度 11%”；反馈仅“已分派给林晓”，不带已分派任务名称。
- 来源：`src/app/components/_fusion/composition-workflow.tsx:113–118`，四个任务标题循环，进度为 task / 9。
- 影响：看起来下一项任务已经完成 11%，实际表达的是已用分派容量；用户也难确认刚刚分派的究竟是哪项。
- 建议：标明“已分派 1 / 9 项”，把待分派任务独立显示；反馈应包含刚完成分派的任务名和成员。最好提供九项真实示例任务，避免四个名字循环。

### 6. P2：不同资源的用量相加却统一标为 GB·h

- 类型：数据表达缺陷，浏览器确认。
- 路径：`/cases/chart#interaction-157`。
- 结果：“存储 / 接口 / 模型”，总计 807 GB·h；切换接口也以 GB·h 展示。
- 来源：`src/app/components/_fusion/agent-charts-plots.tsx:67–74`。
- 影响：调用次数、模型消耗和存储时长不能直接相加，图表示例会给出貌似准确但无法解释的总量。
- 建议：改为同单位的三类资源（例如项目 A/B/C 的存储占用），或统一到清楚说明的计费积分/费用，再计算累计与占比。

## 展示整理建议（非功能阻塞）

`/cases/card` 仍先铺大量同构卡片的主题、尺寸与 icon 组合，夹有 Themes (sm)、title + action、no logo 等说明，新的组合位于很长页面末尾。这延续了用户所说“大小、数量、排版乱”的问题。建议案例页每类一到两个代表组合，主题由统一控件切换；完整参数矩阵移到组件参考页。此处是展示建议，不应与上面的浏览器功能错误合并计数。
