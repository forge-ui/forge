# Forge 页面视觉与交互审查

目标是判断页面是否正确呈现 Forge 的设计，而不是只检查是否导入组件或使用 fg-*。组件来源、真实导出和 Token 接入是基础检查，不能代替以下审查。按本次授权页面执行，不扩成全库改造或专项测试。

## 依据与判定

优先遵循用户明确决策与目标项目当前适用标准，再核对安装版本的 Token、组件类型/源码和匹配案例；旧宿主约定不能覆盖当前标准。先确定页面业务角色和对照案例，记录版本及有意差异。案例是结构参照，不要求业务页面逐像素复刻。无明确依据的审美判断写成建议，不宣布为违规或已获批准。

| 维度 | 必须观察的实际效果 | 常见漏检 |
|---|---|---|
| 配色 | 品牌/强调色、文字层级、背景、边框、状态与反馈语义；可读性及主题内一致性 | 都是 fg-* 仍可能主次颠倒、正文过浅、状态仅靠颜色 |
| 圆角与外形 | 对应组件的尺寸档、圆角、边框、阴影与图标尺度；嵌套和组合后的轮廓 | 自定义覆盖破坏形态；不应把所有控件统一同一个圆角 |
| 字体与字号 | 实际字体与回退、字号、字重、行高、标题/正文/说明层次、金额与数字对齐 | 组件外框正确，内部继承错误字体或字号；中文和长文本显示异常 |
| 布局与密度 | 内容宽度、对齐、内外间距、分组、阅读顺序、留白、滚动归属及容器不足时重排 | 双重 padding、固定空白、主要操作被挤掉、整页横滚；不把容器预算当视口断点 |
| 整体风格 | 页头、工具带、主体、内容子组件与弹层形成一致层次；装饰服务业务 | 单个组件正确，组合后仍杂乱；卡片、胶囊、阴影与强调滥用 |
| 交互与反馈 | 主次操作、适用的加载/空/错误/禁用/成功、校验与输入保留、未保存保护、弹层关闭、键盘焦点与滚动可达 | 有按钮但无反馈；子层关闭牵连父层；关闭后焦点丢失；未实现能力假装成功 |

状态表达另读 [状态规则](status-presentation.md)，组件组合另读 [组件组合规则](component-recommended-standard.md)，页面预算另读 [页面推荐](page-recommended-standard.md)。尺寸、字体和圆角按实际版本取值，不将某张截图的测量值固化为跨版本规则。

## 取证方式

1. 先看整页结构和区块，再看组件内容层。检查源码、props、样式覆盖及继承，确认 Token 和组件实际生效。
2. 在实际浏览器打开授权页面的主要状态，观察实际显示并操作关键路径；按业务选代表性的宽、窄容器，短屏只在弹层等相关场景核对。复用现有 Chrome，遵循目标项目 AGENTS.md；未获许可不另起系统 Chrome 或独立 profile。
3. 对字体、颜色、圆角、尺寸等疑点读取计算样式并与当前版本案例对照。截图记录视觉，操作结果记录交互；静态截图不能证明键盘、反馈或关闭行为。
4. 对自定义单元格、详情正文等检查配套内容组件和实际排版。不能因为用了 DataTable、Modal、Drawer 或 fg-* 就判整页通过。
5. 只检查业务适用状态；无真实接口时明确演示边界。读屏、物理触摸、完整无障碍/对比度检测等没有执行就标未验证，不以目视替代，也不自动扩成新增交付门槛。

## 报告与收口

用普通中文先说明页面会怎样呈现、哪里影响阅读或操作，再给必要证据。六个维度分别记录：符合 / 需修正 / 设计建议 / 未验证；同一维度可同时有已验证与未验证部分，确实不适用时说明理由。每个问题给位置、依据、影响和修正建议。不能以总分掩盖阻断操作的问题。

客观偏离在授权范围内修正并重验；常规技术选择给推荐；只有真实设计偏好或标准冲突需用户选择，并给直观对照及影响。未授权修复时只报告。验收画面必须代表当前推荐效果，旧图标历史/现状，示意图标推荐结构，真实组件展示单独说明。

结论区分“已修正并验证”“建议采用”“未验证”“用户已验收”。技术检查通过不代替视觉与交互证据，审计通过不代替用户验收；未完成浏览器检查时只能给静态审查结论。不得顺手修改 Core、实现新业务或提交发布。
